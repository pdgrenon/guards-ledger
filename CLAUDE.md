## Architecture

Single-page React 19 app (Vite) for tracking game state in *The Isofarian Guard* board game. Deployed to Cloudflare Pages at `https://isofarian.averageideas.dev`.

### State management

All game state lives in one custom hook: `src/hooks/useGameState.js`. It owns:
- loading from / saving to `localStorage` key `guards_ledger_v2` after every action
- all action callbacks (validate → mutate → log → return new state)
- export/import of full state as a dated JSON file (`guards-ledger-save-YYYY-MM-DD.json`), downloaded via the shared `downloadJson` helper in `src/utils/downloadUtils.js`
- wiring each action to its sync section via `useSupabaseSync`

All pure state logic is extracted into `src/hooks/gameReducers.js` — no React, no localStorage, no side-effects. This makes reducers trivially unit-testable. `useGameState` is a thin wiring layer on top.

**Every mutating action logs (AVE-940).** Twelve campaign/party reducers plus the Fort Istra building action used to produce no entry at all, so the session log recorded HP and stash changes but not one campaign milestone — and `deriveUndoLabel`, which prefers the new log message, fell back to a bare `"Campaign update"` for eleven distinct actions on the one control whose purpose is recovering from a mis-tap. Conventions to keep when adding an action: campaign-section messages start with the literal `Campaign` and party ones with `Party`, because `classifyEntry` (`MoreTab.jsx`) keys off the **first word** and those two land in the `system` / `party` classes respectively — matching the existing entries and avoiding a repeat of AVE-367's border/colour disagreement. Completion reducers receive only an id, so they resolve a human label through the static data modules (`encounterLabel` / `bountyLabel` / `puzzleQuestLabel`), each falling back to the raw id rather than emitting `undefined`. `encounterLabel` reads the small `ENCOUNTER_NAMES` map, **not** `encounters.js` — see the chunk-boundary note under Static data. The "set"-style reducers (`reduceSetCampaignLocation`, `reduceUpdateDynamicLocation`, `reduceSetCampaign`, `reduceSetFtIstraBuilding`) return `s` unchanged on a no-op write — `DraftInput` re-commits on blur, and without the guard a no-op would spam the log, wipe the undo snapshot, and fire a sync write (AVE-536). `addLog` defaults a missing `state.log` to `[]`: now that most actions log, a state missing a local-only key must not take down the mutation itself.

**`reduceSetFtIstraBuilding` lives in `gameReducers.js`, not inline in `useGameState`.** It was written as an inline updater, which is exactly why AVE-925 missed it. Its state shape is unchanged — `ftIstraBuildings` is a growable map whose undo path depends on the map-tombstone rules. **`reduceToggleExpandedSatchel` was the last one left inline** and was consequently also the one mutating action producing no log entry at all, so the session log recorded items going into and out of the hidden slots but never the toggle that hid them, and Undo could only offer `deriveUndoLabel`'s generic `"<Guard> update"`. It is now a reducer like every other action, logs `"<Guard> satchel expanded/collapsed"` (guard name first, so `classifyEntry` gives it the guard border), and returns `s` unchanged for an out-of-range index. **There are no inline updaters left in `useGameState` — keep it that way**; an action that lives there is an action the reducer tests do not see.

`gameReducers.js` also owns the **per-section shape healers** (`healGuard`, `healResourcesSection`, `healCitiesSection`, `healPartySection`, `healStashSection`, `healCampaignSection`, dispatched by `healRemoteSection`). Both consumers share them so the two can't drift: `healState` composes them on the load path (layering the cross-section legacy-flag migrations on top), and `applyRemoteSection` calls `healRemoteSection` on every section arriving from Supabase (AVE-873). Before that, only local loads were healed — the components dereference `campaign.plans`, `campaign.locations`, `guard.equipment` and friends without guards *because* `healState` guarantees them, so a malformed remote section threw on render, dropped the tab into its `ErrorBoundary`, and survived the reload because the save effect had already persisted it. Two rules when touching these: healing a **healthy** section must be a deep-equal no-op (`applyRemoteRow`'s echo suppression compares `deepEqual(incoming, extractSection(local))`, so an added, renamed **or dropped** key would make every echo look like a real remote change — dropping is not the safe direction, see the stonebound `type` note below and AVE-922), and they do shape/type repair **only** — never the load-time legacy migrations, which need `cities` and `campaign` together. Coverage: `src/hooks/remoteSectionHealing.test.jsx`.

**"Healthy" means *anything a reducer can produce*, not just a factory's output — the invariant is a contract on the reducers as much as on the healers.** Clearing a satchel slot used to leave the old count behind (`{ item: '', qty: 4 }`) while `healGuard` forces `qty: 1` on any slot with an empty item, so the campaign row kept 4 and every local load healed to 1. That guard's section then differed from the server permanently: each boot/foreground `refetchRow` saw a "change", applied it (firing `onRemoteChange`, which wipes the undo snapshot and re-renders), and healed it straight back — self-inflicted AVE-922, with no bad save or unmigrated row needed. `reduceSetGuardSatchelItem` now resets `qty` to 1 when the item is cleared. When adding a reducer, walk it in `src/hooks/gameReducers.healIdempotence.test.js`, which asserts every healer is a deep-equal no-op on real reducer output. Note the two directions this can break from: a healer that rewrites too much, **or** a reducer that emits a value the healer disagrees with.

Every healer **clamps** to the range its consumers assume; `healEventToken` is the one that has to (0–3), because `reduceSetEventToken` clamps there and `EventTokensCard` renders exactly three pips, treats `>= 3` as triggered, and disables `−` at `0`. A bare `healNumber` accepted any finite value, so `mountain: 99` from a damaged save or an unmigrated row rendered a permanently triggered region whose only control is "Resolve event". Clamping is always the safe direction — it is identity on in-range values, so it cannot break the deep-equal rule above.

`App.jsx` calls `useGameState()` and passes state + action callbacks down via props. There is no context, no state library — pure prop drilling.

#### State shape and sync sections

State is flat at the top level (no nesting by section). Sections are a conceptual grouping that maps to Supabase columns for sync purposes:

| Section | State keys | Supabase column |
|---|---|---|
| `resources` | `sil`, `lux` | `resources` |
| `cities` | `cities` | `cities` |
| `party` | `activeParty` | `party` |
| `guard_0` … `guard_7` | one element of `guards` each | `guard_0` … `guard_7` |
| `stash` | `stash`, `stonebound` | `stash` |
| `campaign` | `campaign` | `campaign` |
| local-only | `log`, `settings`, `activeGuardIdx` | — not synced — |

**Guards are split into one column per guard (`guard_0` … `guard_7`).** Each guard mutation in `useGameState` syncs to only that guard's column via `guardColumn(idx)`, so two players editing different guards at the same time never overwrite each other (AVE-83). The local state shape is unchanged — `state.guards` is still a flat 8-element array; the split exists only at the sync/column boundary. The shared two-element party selection (`activeParty`) lives in its own `party` section.

`activeGuardIdx` is local-only even though it lives alongside guards in state. It tracks which guard tab each player is viewing — a per-device UI concern, not shared campaign data. `setActiveGuard` passes `null` as the section name so it never triggers a sync upsert. `handleRemoteChange` in `useGameState` and the section maps in `useSupabaseSync` both exclude it so it is never overwritten by a remote update.

Each action in `useGameState` calls `setState(reducer, sectionName)` where `sectionName` is the section that action modifies. `setState` persists to localStorage and calls `sync.upsertSection(sectionName, nextState)` in one step.

**`setState` computes the next state outside the `setRaw` updater and passes `setRaw` a plain value — never a function (AVE-582, AVE-875).** A React state updater must be a pure function of `prev`: React may call it more than once and may discard the render it produced. Mutating `undoSnapshot.current` or calling `setUndoLabel` from inside one runs those effects for renders that never commit, which leaves Undo offering a restore to a state the player never saw — and `undoLastAction` doesn't just `setRaw` that snapshot, it `upsertSection`s it to the shared campaign row. `handleRemoteChange` follows the same rule. Because both read `stateRef.current` rather than React's `prev`, **`setState` advances `stateRef.current` synchronously before calling `setRaw`**: the ref is otherwise only refreshed by an effect after commit, so two `setState` calls dispatched in one event would both read the same stale value and the second would silently discard the first. Treat that assignment as load-bearing — removing it breaks same-event batching (covered by `useGameState.setStatePurity.test.jsx`). The post-commit `stateRef` effect stays as the backstop for the paths that call `setRaw` directly (`leaveCampaign`, `undoLastAction`).

**`setState` bails out entirely when the reducer returns `prev` unchanged (AVE-536 follow-up).** The "set"-style reducers each guard their own no-op write, but that guard only ever suppressed the *log entry*: `setState` went on to overwrite `undoSnapshot`, call `setUndoLabel`, add the section to `pendingSections`, and dispatch a `merge_section` write for a section nothing had changed in. The reachable symptom is a tap on an already-selected control — the active button in `CampaignProgressCard`, or the active state pill on a Ft. Istra `BuildingCard`; both are plain buttons that fire on every tap — which threw away the player's pending undo and replaced it with a snapshot of the state they were already in, labelled `"Campaign update"` (`deriveUndoLabel`'s generic fallback, reached precisely because no log entry was added to name it). A reducer returning its input is the app's one signal for "nothing happened"; treat it as such at the single choke point rather than in each caller. Coverage: `src/hooks/useGameState.noopWrites.test.jsx`.

**The local save is flushed on `beforeunload`, `pagehide`, AND `visibilitychange: hidden` — one handler, three registrations (AVE-936).** The save effect is debounced 400ms, and `beforeunload` alone does not cover the app's primary platform: mobile browsers routinely discard a backgrounded tab, and kill a swiped-away standalone PWA, without ever firing it. The hidden path used to call `flushPendingSync` only, which is the *sync* half — and `enqueuePendingSections` returns immediately when no campaign is active, so in solo mode (the default, and the only mode without Supabase env vars) hiding the tab did nothing durable and the last edit was lost. In campaign mode it was worse than lost: the queued payload reached the server on the next boot while local `localStorage` still held the older value, and `applyRemoteRow`'s pending-queue guard then skipped the correcting section. The handler must never touch React state — the component may be tearing down — which is why it ignores `saveState`'s return value. Coverage: `src/hooks/useGameState.persistence.test.jsx`.

**A failed full-row replacement is surfaced and retryable, never console-only (AVE-937).** `importState`, `resetState`, and `loadDemoData` all push through the shared `pushReplacement(next, label)` helper, which sets `replaceError` on failure (and has a `.catch` — the old `.then()`-only chains turned a rejection into an unhandled promise rejection). `App.jsx` renders a `role="alert"` banner with **Retry** (`retryReplacement`, re-sends the same held state) and **Dismiss**. This matters because a failed `replaceRow` is silent by construction: it returns before the `lastSeenTs` seeding line, so the server row's timestamps still equal our baseline and `sectionChanged` skips every section on the next refetch — local and server diverge permanently, and the next ordinary edit deep-merges into the stale row, producing exactly the AVE-374 chimera. The `error` status `replaceRow` sets is not enough on its own; see the `flushQueue` note under Sync.

**`replaceRow` clears the pending upsert queue before it writes (AVE-374 follow-up).** A replacement rebuilds the whole of local state, so every payload still sitting in `pendingQueue` (queued offline, or re-queued by a failed write) is unreachable from the new state — dead data. Left there, the next `flushQueue` pushes it through `merge_section`, whose deep merge folds the pre-replacement ledger back into the freshly replaced row, and `applyRemoteRow`'s pending-queue guard then suppresses the row that would have corrected local, so the divergence is invisible on this device too. The generation gate (AVE-527) only delays that: the stale write is rejected, re-queued, and the refetch it triggers adopts the new generation, so the retry commits. `joinCampaign` and `leaveCampaign` already clear the queue for the same reason. Coverage: `src/hooks/useSupabaseSync.replaceRow.test.jsx`.

#### localStorage versioning and migration

- Current key: `guards_ledger_v2`
- Previous key: `guards_ledger_v1` (flat shape, no section factories)
- On first load, if `v2` is absent but `v1` is present, `migrateV1()` in `useGameState.js` converts the old save and writes it under the new key. Migration runs once.
- `importState` also accepts v1-format JSON exports via the same migration path. **It first gates the parsed blob through `looksLikeSave` (AVE-869)** — a structural check for at least one of `guards` / `cities` / `campaign` / `stash`. `healState` cannot serve as that check, because import hands it `migrateV1(parsed)` and `migrateV1` `??`-defaults every field it reads: it launders a string, a number, an array, or any unrelated object into a fully-formed default state, so `healState` never returns `null` and the `Invalid save file.` branch was unreachable for anything that parsed as JSON. Import is destructive and unrecoverable (it clears the undo snapshot and `replaceRow`s the shared campaign row), so picking the wrong `.json` used to silently wipe the ledger for every player. Keep the check **structural, not a strict schema** — `healState` is deliberately tolerant of damaged saves, and the guard must not be stricter than the thing it protects. Validate **before** `migrateV1`, never after.
- `activeGuardIdx` is always reset on load (local-only UI state), but the reset target is the first guard of the saved party (falling back to index 0) — not a hard-coded initial value.
- **The blank ledger `loadState` falls back to on an unrecoverable save comes from `blankLedgerAfterCorruption()`, not `createInitialState()`.** It is the same state with `settings.hasSeenOnboarding: true`, because a corrupted save is proof of a *returning* player — the same reasoning `healSettings` applies to a save predating the onboarding key. Booting `createInitialState()` as-is left the flag `false`, so `App` rendered the first-run overlay's full-screen backdrop on top of `CorruptionBanner`: Download backup and Import save — the app's only recovery path, and the only route to the raw string that the banner's own Dismiss then deletes — sat unreachable behind a modal whose second button is **Load demo data**. Coverage: `src/hooks/useGameState.corruption.test.jsx`.

### Sync (Supabase Realtime)

`src/hooks/useSupabaseSync.js` owns all Supabase interaction. `useGameState` calls it and receives a `sync` handle; `App.jsx` passes `sync` to `SettingsPanel` for the create/join/leave UI.

**Key behaviors:**
- The Supabase client is `null` when `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` are absent. All sync calls silently no-op. The app runs as a fully local tool.
- `sync.upsertSection(sectionName, state)` extracts the relevant keys (or, for a `guard_N` column, that one guard object) and calls the **`merge_section` RPC** (not a raw `UPDATE`) — it never writes local-only keys (`log`, `settings`, `activeGuardIdx`). The server-side RPC performs a **field-level deep merge** of the incoming payload into the existing column, so two players editing different keys in the same section concurrently don't lose each other's writes. The merge is **array-aware**: arrays of `id`-keyed objects (cities, `campaign.plans`, `campaign.locations.sideQuests`, `stonebound.locations`) are merged element-by-id — existing elements preserved, matching ids deep-merged, new ids appended — so concurrent edits to *different* array elements no longer clobber each other. Arrays **not** keyed by id (guard satchel slots, `activeParty`) are treated as a single value: the incoming array replaces the existing one wholesale (last-write-wins), like a scalar field — they used to merge as a set union, but a union can only ever add elements, so a cleared satchel slot merged the old item back in and the Realtime echo resurrected it on the deleting client (AVE-362). An empty incoming array preserves the existing value (ambiguous — nothing to inspect for an `id`; in this app it only ever means "nothing to merge"). The only remaining unmerged case is two players editing the *same* field of the same key/array element (or the same non-id array) at the same instant (a CRDT problem, accepted limitation). See `supabase/migrations/0002_field_level_merge.sql` (object merge), `supabase/migrations/0003_array_merge.sql` (array merge), and `supabase/migrations/0005_plain_array_lww.sql` (non-id arrays last-write-wins) for the merge functions. (AVE-94, AVE-197, AVE-362.) **The read-merge-write is a single atomic statement**, not a separate `SELECT` followed by a computed `INSERT`/`UPDATE` (AVE-373): `merge_section` does `insert into campaigns as c (...) values (...) on conflict (id) do update set <section> = deep_merge_jsonb(c.<section>, excluded.<section>)`, so `c.<section>` is read as part of the same locked write instead of an earlier, separately-fetched read. Two players writing the *same* section concurrently used to be able to both read the old value, merge independently, and have the second write's `INSERT` silently overwrite the first player's already-merged result — losing an edit even though the two writes touched disjoint keys, the exact case field-level merge exists to protect. Postgres serializes concurrent `INSERT ... ON CONFLICT DO UPDATE` against the same row, so the second call now always merges against the first's already-committed result. See `supabase/migrations/0006_atomic_merge_section.sql`.
- **Array-element deletions in id-keyed arrays use tombstones, not removal (AVE-287).** Because the by-id merge is append-only, a hard-deleted element is restored by the merge (and re-applied by the Realtime echo) whenever a campaign is active. So the delete reducers (`reduceDeletePlan`, `reduceRemoveDynamicLocation` for side quests/bounties, `reduceRemoveStoneboundLocation`) mark the element `{ ...el, deleted: true }` instead of filtering it out; the by-id merge carries that flag onto the matching element like any other field edit, so the delete propagates while concurrent adds of other ids still survive. **All read sites filter `deleted` elements out** (render, counts, cube-budget math, derived inputs) — `CampaignTab` (plans, side quests), `CitiesTab` (bounties), `StashTab` (stonebound locations + cube-budget math; `updateStoneboundLocation` keys off `loc.id`, so tombstoned rows are simply filtered out). `campaign.completedEncounters` was a plain string array with no id, so it is stored as an **id-keyed array of `{ id, deleted? }`** objects (un-completing marks `deleted: true`, re-completing clears it) and rides the same by-id merge — read via `isEncounterCompleted(list, id)` in `gameReducers.js`. Pre-AVE-287 saves (string arrays) are converted on load by `normalizeCompletedEncounters` (used in `migrateV1`/`healState`) and unmigrated remote rows by `normalizeRow`. The one-time DB conversion is `supabase/migrations/0004_tombstone_deletes.sql` (data-only — no function change, since id-keyed deep-merge already carries the flag). **Completing writes the flag explicitly (`deleted: false`), never a bare `{ id }` — the "A Feud between Guilds" revert loop.** The by-id merge deep-merges matching elements, and the deep merge preserves keys absent from the incoming element, so a bare `{ id }` sent against a server-side tombstone leaves `deleted: true` in place; the write's own Realtime echo (carrying the still-tombstoned element, which matches neither current local state nor the self-write buffer, and passes the timestamp gate because our own write bumped `campaign_updated_at`) then reverts the completion on the very client that made it ~1s after every attempt — permanently, for that one element. All three completion toggle reducers (`reduceToggleEncounterComplete`, `reduceToggleBountyComplete`, `reduceTogglePuzzleQuestComplete`) therefore emit `{ id, deleted: false }` on complete (both the re-complete and first-complete/append branches), and `normalizeCompletedEncounters` preserves an explicit `deleted: false` instead of stripping it to `{ id }`, so a reloaded local value still deep-equals the server row/echo and the value-based echo suppression keeps working. The delete-only tombstone arrays (plans, side quests/bounty locations, stonebound locations) are unaffected — their ids are never resurrected. Merge-model regression tests: `src/hooks/tombstoneMerge.test.js`.
- **Locally-created array-element ids come from `newId()` in `src/utils/ids.js` — never `Date.now() + Math.random()`.** Those ids *are* the merge key for everything in the bullet above, so a duplicate is not a cosmetic React-key problem: `merge_jsonb_array_by_id` collapses the pair into one element for every player, an edit by id hits whichever matches first, and a tombstone delete marks both. The old generator looked like it had 2^53 of range and did not — `Date.now()` is ≈1.79e12, where the spacing between adjacent doubles is ≈0.0004, so almost all of `Math.random()` is truncated on the way in. Measured: **200,000 draws inside one millisecond produce 4,097 distinct values**, a ~1/4096 collision for any two ids created in the same millisecond. A human tapping "+ Add plan" never hit it (taps are ~100ms apart, so `Date.now()` alone separated them); it surfaced as an intermittent failure in `reduceUpdateStoneboundLocation`'s "finds the target by id" test, which adds twice in a loop. `newId()` uses `crypto.randomUUID()` and falls back to timestamp + **monotonic session counter** + random suffix — the counter, not the randomness, is what makes the fallback safe, and the fallback exists because `randomUUID` is undefined outside a secure context (the dev server over `--host` on a plain-http LAN address, which is how this app gets tested on a phone). Coverage: `src/utils/ids.test.js` plus the tight-loop suite in `gameReducers.test.js`, both verified to fail against the old generator.

  Two things not to do here. **Ids are now strings; pre-existing saves keep their numeric ones and must not be migrated** — rewriting an id changes the merge key, so every element would look new to the server while the originals stayed behind as orphans. Mixed types are fine because every lookup compares an id taken from the same array. And **do not add an id type check to a healer**: `healStashSection` already accepts `string | number` for exactly this reason, and `healCampaignSection` puts no constraint on `plans` — tightening either would delete a player's data on load.
- When offline, upserts are queued in a `Map` (keyed by section name, so later writes replace earlier ones for the same section). The queue is flushed automatically on reconnect via the `online` event. Each queued section is sent through `merge_section` independently on flush. **After a successful batch, `flushQueue` deletes an entry only when the queued payload is still the exact object it sent (identity, not section name).** `entries` is snapshotted before the first await, and the queue can pick up a *newer* payload for the same section while the batch is in flight — `upsertSection` routes straight to the queue when `navigator.onLine` is false, and a generation rejection re-queues. Deleting by key threw that newer edit away without ever sending it, and since `applyRemoteRow` skips sections that are still queued, dropping the entry also removed the guard keeping the next `refetchRow` from reverting the edit to the older server value. `extractSection` builds a fresh object per call, so identity is an exact "unchanged since dispatch" test; a false negative only costs one redundant write. Coverage: `src/hooks/useSupabaseSync.flushQueue.test.jsx`.
- `useGameState`'s debounce collects a **set** of pending sections per window and flushes each — so editing two different guards within one debounce window upserts both columns rather than dropping one.
- Inbound Realtime updates are filtered by **two independent guards** before a section is applied (AVE-314). Realtime delivers the *entire* row on every UPDATE, but `merge_section` bumps only the changed section's `<section>_updated_at` timestamp, so most sections in any given payload are stale filler:
  1. **Per-section timestamp gate** (`sectionChanged`): a section is skipped unless its `<section>_updated_at` is **strictly newer** than the last value we saw (`lastSeenTs`, seeded on join/create). This stops another player's edit to one guard from carrying a *stale* value of a guard you're actively typing into and clobbering your in-flight keystrokes — the dominant two-player symptom. The comparison is **ordered, not just unequal** (`ts > prev`, AVE-526). It runs on **epoch milliseconds via `tsToMs`, never on the raw strings** (AVE-868): the `_updated_at` columns are `timestamptz`, and the same instant reaches the client in three different renderings — Realtime delivers raw Postgres text (`2026-07-29 15:30:00.654321+00`, since `@supabase/realtime-js`'s `convertCell` applies its space→`T` fix only to `timestamp`, not `timestamptz`), PostgREST returns ISO-8601 (`2026-07-29T15:30:00.654321+00:00`), and `buildFullRow` writes `new Date().toISOString()` (`…Z`). Comparing those lexicographically is not chronological: `' '` (0x20) sorts below `'T'` (0x54), so every Realtime stamp ranked below any same-date REST one, and once AVE-372's boot/foreground `refetchRow` seeded the baseline the gate silently dropped **every** live update for the rest of the UTC day. `tsToMs` normalizes both Postgres-isms (the space separator and the bare two-digit `+00` offset, neither of which `Date.parse` accepts) and falls open on an unparseable value. An `!==` test would also pass an *older* timestamp — the case where a slow `refetchRow` SELECT resolves *after* a newer Realtime event for the same section already applied, carrying the pre-edit value and rolling back another player's just-applied update (this device has no self-write for a remote player's edit, so `hasNewerSelfWrite` can't catch it). Correspondingly, `applyRemoteRow` advances `lastSeenTs` **monotonically** via `mergeSeenTimestamps` (keep `max(existing, incoming)` per section) rather than overwriting — a stale row must not regress the baseline and weaken the gate for the next event.
  2. **Value-based echo suppression**: for a section that did change, it is still skipped if the incoming value deep-equals current local, **or** matches one of our own recently-sent writes (`reconcileSelfEcho` / the `selfWrites` buffer). The self-write buffer catches an echo of an *earlier* keystroke that arrives after local has moved on to a *later* one — value-equality against current local alone can't (it no longer matches). This replaced the older 3-second wall-clock window that dropped legitimate concurrent changes (AVE-82, AVE-84); both guards remain timing-independent (the self-write TTL only bounds buffer growth, it is not a suppression window).

  If **no** section survives both guards (the common case: an echo of our own write), `onRemoteChange` is **not called at all** (AVE-371) — forwarding no-op events made `useGameState` wipe its undo snapshot within a second of every local action while a campaign was active, and forced a full re-render per echo.
- On `joinCampaign`, the full remote row is fetched (and passed through `normalizeRow`) and every section in `ALL_SECTIONS` is merged into local state; the per-section timestamp baseline (`lastSeenTs`) is seeded from the fetched row. `log`, `settings`, and `activeGuardIdx` are preserved from local.
- **`refetchRow` pulls the current row on boot, reconnect, and foreground (AVE-372).** Resubscribing after a dropped socket only delivers *future* events — never the UPDATEs missed while disconnected — so after a phone lock, an `online` reconnect, or a cold boot with a campaign already active, local state (which on boot comes purely from localStorage) could sit stale indefinitely until the other player happened to edit again. `refetchRow` selects the row and pushes it through **the same gated pipeline as a Realtime event** (`applyRemoteRow`: `normalizeRow` → per-section timestamp gate → value/self-echo suppression → `applyRemoteSection` → advance `lastSeenTs` → `onRemoteChange` only if a section applied). It is called once on mount when `campaignId` already exists, and after `subscribe()` in both the `visibilitychange` and `online` handlers. The boot fetch also seeds `lastSeenTs` (which otherwise only join/create seed), so the first subsequent Realtime UPDATE on a plain reload has a real timestamp baseline to gate against instead of applying blind. `applyRemoteRow` is the extracted pipeline shared by `refetchRow` and the Realtime UPDATE handler.
- **A remote section can still race a local edit that hasn't been sent yet — closed in `useGameState`, not `useSupabaseSync` (AVE-518).** The AVE-314 guards above only recognize echoes of writes we've actually *dispatched* (`noteSelfWrite` is called when `upsertSection` fires, ~400ms after the local optimistic update, once `setState`'s debounce elapses). A local edit still sitting inside that debounce window is invisible to them. If a remote section arrives in that window — `refetchRow`'s boot/foreground pull landing before our own pending write went out, or a genuine edit from another player to the same section — it used to be applied wholesale over the fresh local value via `applyRemoteSection`, silently reverting it a moment later. This is what made marking a Bounty Quest complete right after opening/resuming the app flip back to incomplete about a second later (the foreground `refetchRow` was still in flight when the tap landed). `useGameState`'s `handleRemoteChange` fixes this the same way `merge_section` protects the server side: `mergeRemoteSections` (exported from `useGameState.js`) skips any section still present in `pendingSections` (the same debounce-tracking `Set` `setState` uses) before calling `applyRemoteSection`. Once the debounce flushes and the write is dispatched, the section leaves `pendingSections` and the existing timestamp/echo gating in `useSupabaseSync` takes over as usual.
- **A *slow* `refetchRow` can still race a write that has already been dispatched (AVE-518 follow-up).** The `pendingSections` guard above only covers the window before a write is dispatched. `refetchRow`'s SELECT is a plain HTTP request — on a slow connection (mobile foregrounding after boot is the common trigger) it can still be in flight when the user's edit clears `pendingSections` and dispatches its own write, and go on to resolve *after* that write's own self-write echo has already been recognized and consumed. Its stale payload then matches neither current local state (which has the newer edit) nor any buffered self-write (the values genuinely differ — the fetch predates the write), so it slipped through both AVE-314 guards and clobbered the newer edit. `refetchRow` now captures `requestedAt = Date.now()` before dispatching the SELECT and passes it into `applyRemoteRow`, which skips any section for which `hasNewerSelfWrite` finds a self-write dispatched at or after that time — using only this device's own clock, no cross-device timestamp comparison needed. This is additive to the `pendingSections` guard, not a replacement: one closes the pre-dispatch window, the other closes the post-dispatch (in-flight-request) window.
- **All four Realtime subscribe states are handled, and the status callback checks it still owns the live channel (AVE-938).** `channelRef.current` is published **before** `channel.subscribe(...)` is called, not after: the ownership check compares against the ref, so assigning it afterwards left a window in which a status emitted synchronously from `subscribe()` (an immediate `CHANNEL_ERROR`) saw the *previous* channel, failed the check, and returned — swallowing the failure and leaving `channelDown` unset with the badge on green. `@supabase/realtime-js` emits `SUBSCRIBED | TIMED_OUT | CLOSED | CHANNEL_ERROR`; only the first and last used to be handled, so `TIMED_OUT`/`CLOSED` left `syncStatus` on `'idle'` — which `SyncBadge` renders as a green **"Synced"** — while inbound updates had silently stopped. Outbound writes are unaffected (`merge_section` is plain HTTP), so nothing else looks wrong: the badge is the only signal, and it was reporting the opposite. The ownership check (`if (channelRef.current !== channel) return;`) is load-bearing: `subscribe` removes the previous channel first and `removeChannel` makes *that* channel emit `CLOSED`, so without it every foreground and every reconnect would flag a spurious error. A channel failure sets `channelDown` and the `syncError` string `'Live updates disconnected — reconnecting…'`.
- **The AVE-376 backoff ladder calls `recoverSync`, not `flushQueue` (AVE-938).** `flushQueue` retries queued *writes*, which does nothing for a dead socket — and resubscription otherwise only happens on `online`, foreground, or a campaign change, none of which fire for a tab left foregrounded on a table through a wifi blip. `recoverSync` resubscribes and `refetchRow`s (resubscribing alone only delivers *future* events — AVE-372) **only when `channelDown` is set**, then flushes; the pure write-retry case is unchanged.
- **`flushQueue`'s empty-queue branch is gated on `channelDown` and `replaceFailed`.** That branch clears a stuck `'error'` status back to `'idle'` because an error with an empty queue has nothing to retry (AVE-871) — correct for its own case, but two failures never produce a queue entry and *are* retryable: a dead channel (AVE-938) and a failed `replaceRow` (AVE-937, which is a raw `UPDATE` and deliberately never queued, since queue entries deep-merge and would rebuild the chimera). Without the gate the ladder fired ~1s later, found an empty queue, and parked the pill on green while sync was dead or the row was diverged. Both refs are cleared by `leaveCampaign`, and `replaceFailed` also by `joinCampaign`.
- **`joinCampaign` distinguishes a wrong code from an unreachable server (AVE-942).** It returns early when `isOnline.current` is false (no request at all), and only `error.code === 'PGRST116'` — PostgREST's "no rows" for `.single()` — reports the not-found message, which echoes the **normalized** id so a legacy dashless `WOLF42` is visibly not `WOLF-42`. Every other error (network, captive portal, RLS, a database missing a migration — AVE-870) reports a connection problem with `error.message` attached. The single `if (error || !data)` branch it replaced told players to re-read a correct code, and the natural next move — tapping **Create** — abandons the campaign the group was actually in.
- Realtime subscription uses `postgres_changes` filtered to `id=eq.{campaignId}`. On `UPDATE`, each remote section in `ALL_SECTIONS` is applied to the current local state subject to the timestamp gate + echo suppression above; local-only keys are preserved.
- `normalizeRow` reshapes a pre-AVE-83 row (single `guards` blob `{ guards:[…], activeParty:[…] }`) into per-guard columns + `party` on read, so the client tolerates a database that hasn't yet had the `supabase/migrations/0001_split_guards_per_column.sql` migration applied.
- Campaign IDs are a 4-letter word prefix, a hyphen, and six random alphanumerics (e.g. `WOLF-7F3K9Q`), stored in `localStorage` under `guards_ledger_campaign_id`. Pre-AVE-104 ids were 6 bare alphanumerics (`WOLF42`) and are still valid. **A code entered by a player is passed through `normalizeCampaignCode` before the lookup (AVE-786)** — it strips every non-alphanumeric character (spaces, hyphens of any Unicode flavor, stray punctuation), uppercases, and reinserts the hyphen after the word prefix *only* when the stripped result is exactly 10 characters. Codes get read aloud across a table, so a dashless `WOLF7F3K9Q` is the common entry and used to miss the exact-match lookup and report "Campaign not found" for a perfectly correct code. The length check is what keeps a legacy `WOLF42` from being mangled into `WOLF-42`, which would match nothing. Normalization lives in `useSupabaseSync`, not in the input's `onChange` — reformatting under the cursor while typing is hostile, and every caller of `joinCampaign` gets the benefit. The **normalized** id is what gets stored, never the raw input.

**`sync` handle shape** (returned by `useSupabaseSync`, exposed via `useGameState`):
```js
{
  campaignId,       // string | null
  syncStatus,       // 'idle' | 'syncing' | 'error' | 'offline'
  syncError,        // string | null
  upsertSection,    // (sectionName, state) => void
  createCampaign,   // () => Promise<{ id, error }>
  joinCampaign,     // (code) => Promise<{ state, error }>
  leaveCampaign,    // () => void
  isConfigured,     // boolean — false when Supabase env vars are absent
}
```

### Component structure

- **`App.jsx`** — shell: tab nav (`Guards`, `Cities`, `Stash`, `Crafting`, `Campaign`, `More`), top bar, party switcher, session log view, settings overlay trigger. Also owns `sourceItem` state and renders `MaterialSourcePopup` at the app level so it overlays everything correctly. Passes `sync={game.sync}` to `SettingsPanel`. When a campaign is active, shows a **campaign pill** in the top bar with the campaign code and a sync-status dot (green/amber/gray/red); tapping it opens Settings scrolled directly to the Multiplayer section. Log messages are colorized via `colorizeLogMessage` — guard names are highlighted in their identity color, "Party" and "Stash" in brand ochre; each log entry also has a colored left border keyed to the same classification.
- **`GuardPanel.jsx`** — HP number display, combat stats (Atk/Def with equipment bonuses shown), equipment, satchel
- **`CitiesTab.jsx`** — city grid: prestige pips (derived, not stored) + quest checkboxes
- **`StashTab.jsx`** — party resources (Sil/Lux), stonebound cube tracker, Fort Istra stash. Stash items show inline "upgrades into →" hints when they are a prereq for a recipe (from `PREREQ_UPGRADES_TO` in `prereqUpgrades.js` — **not** from `recipes.js`; see the chunk-boundary note under Static data). Supports custom items (arbitrary strings not in the predefined list, tracked in a separate "Custom items" category). Accepts `onShowSource` prop; tapping a material name with source data calls it.
- **`CraftTab.jsx`** — stash-aware recipe reference; filters by type, city, star tier, and craftability; search matches item names, material names, cities, and prereq names; combines stash + active guards' satchel contents for craftability checks; applies prestige 2+ material discounts when a city is selected; shows stash-aware "have/need" quantities per ingredient with strikethrough for discounted amounts; hides guard-restricted items unless that guard is in the active party. Accepts `onShowSource` prop; tapping any ingredient name with source data calls it.
- **`MaterialSourcePopup.jsx`** — bottom-sheet overlay showing where to acquire or sell a given material/item. Reads from `MATERIAL_SOURCES` in `materials.js`. Rendered at App level via a `fixed` backdrop. Closes on backdrop tap, ✕ button, or Escape key. No state of its own beyond the `item` prop passed from App.
- **`SettingsPanel.jsx`** — bottom-sheet overlay: active party selectors, per-guard max HP, multiplayer (create/join/leave campaign + sync status), export/import/reset. Accepts `sync` prop from App. **Import JSON is a real `<button>` that programmatically `.click()`s a `display: none` file input held in `fileInputRef` (AVE-785)** — the input is `tabIndex={-1}` + `aria-hidden` so `useDialogA11y`'s focus trap sees exactly one stop for the control. It used to be a bare `<label>` wrapping a `<div>`, which gave the row *no* tab stop at all and locked keyboard-only players out of the app's only recovery path at exactly the moment their save was corrupt. `handleImport` also resets `input.value = ''` after every attempt so re-picking the *same* file still fires `change` (browsers suppress it when `value` is unchanged). **Copy campaign code reports all three outcomes via one `copyStatus` state (`null | 'copied' | 'failed'`) and one 3s reset timer (AVE-789)** — it guards `navigator.clipboard?.writeText` explicitly (undefined in any non-secure context) rather than relying on a synchronous throw, and on failure renders a hint pointing at manual selection. There is deliberately no `document.execCommand('copy')` fallback.
- **`UpdateBanner.jsx`** — shown when a new deploy is installed and waiting (see PWA below). Deliberately `role="status"` and rendered *below* the three `role="alert"` banners: nothing is wrong, and it must not outrank a corrupt save. Reads `src/utils/swUpdate.js` via `useSyncExternalStore`; **Reload** activates the waiting worker, **Later** clears the banner without activating it (the worker stays waiting and takes over on the next natural start). A throwing apply leaves the banner up rather than a dead button — the same rule `downloadJson` follows.
- **`ErrorBoundary.jsx`** — app / tab / guard-level fallbacks. **A boundary holds its caught error until it unmounts, so one that sits in a fixed position needs a `resetKey`.** The guard-level boundary is the case: App renders it in the same slot for whichever guard is showing, so a crash in one guard's panel left the fallback up for *every* guard after it — re-labelled with the new guard's name, blaming a record that is fine — and the fallback's own instruction ("switch to a different guard to keep playing") could not work, leaving the Guards tab dead until a reload. `getDerivedStateFromProps` clears the error when `resetKey` changes; App passes the guard's name. It must stay **keyed**, never an unconditional clear on re-render, or the boundary loops between the fallback and a child that throws again. App- and tab-level boundaries pass no `resetKey` and are unaffected (tabs unmount on switch, which resets them already). Coverage: `src/components/ErrorBoundary.guardReset.test.jsx`.
- **`CorruptionBanner.jsx`** — shown when `loadState` could not parse/heal the save and fell back to a blank ledger (AVE-96). Offers Download backup / Import save / Dismiss. **Its import handler must act on `importState`'s resolved result (AVE-929)** — it used to discard the promise, so a file rejected by `looksLikeSave` (AVE-869) produced no message at all and a *successful* recovery left the red `role="alert"` banner up over the restored ledger, where the next likely tap is Settings → Reset. On failure it renders `result.error`; on success it calls `onDismiss` (= `dismissCorruption`, which also clears the backed-up raw string). It also resets `input.value` after every attempt so re-picking the same file still fires `change` — the AVE-785 fix, which this input never got. The trap it exists to survive: the banner's own Download backup writes `guards-ledger-corrupted-backup-YYYY-MM-DD.json`, one word away from `guards-ledger-save-YYYY-MM-DD.json` in a phone's Downloads list.
- **`CampaignTab.jsx`** — campaign progress, event tokens, locations, plans, Fort Istra buildings. Its `DraftInput` is the draft-until-commit text field for the Locations / Side Quest rows (AVE-784), mirroring `Autocomplete`'s `draft === null` convention so an untouched field still reflects a co-player's inbound edit. **Unlike `Autocomplete`, it calls `e.currentTarget.blur()` from its own keydown handler** (to dismiss the mobile keyboard), and `blur()` fires its event *synchronously* — before React applies the queued `setDraft(null)`. The `onBlur` handler therefore re-enters `commit()` with the same stale `draft`, which made Enter commit twice (the second `setState` snapshotting the post-edit state, leaving Undo a no-op) and made Escape commit the draft it was supposed to discard (AVE-924). `commit()` now reads and clears a `draftRef` — updated in the same synchronous frame that queues `setDraft` — so the re-entry is a no-op regardless of render timing, and it clears **before** invoking `onCommit` (which synchronously reaches `setState`). If you touch this, note that `fireEvent.focus` does **not** move `document.activeElement`, so a test using it cannot observe the blur path at all — the tests use real `input.focus()`.

- **`Autocomplete.jsx`** — reusable searchable dropdown (no external library); max 12 results, case-insensitive. **Draft-until-commit (AVE-534):** keystrokes update an internal `draft` and drive filtering but do **not** call `onChange` — so partially-typed text never becomes committed state and there's no undo/sync write per character. `onChange` fires exactly once at a commit point: selecting an option, Enter, or blur. **Enter resolves in priority order (AVE-872): the explicitly highlighted option (arrow keys) → an *exact* case-insensitive match for the typed text → the top filtered row → `resolveDraft`.** The exact-match rung matters because `filtered` is a substring match in source order and `ALL_MATERIALS` is sorted, so typing a full valid name whose text is contained by an earlier-sorting option used to commit the wrong item — `"Diamond"` committed `"Black Diamond"`, `"Horn"` committed `"Clayhorn Steak"`. Blur always resolved these correctly, so the two commit gestures disagreed on identical input; `exactMatch` is now the single shared definition used by both. On blur/Enter-resolve the draft is resolved: an exact case-insensitive match commits the canonical option string (`"silver flame"` → `"Silver Flame"`); empty commits `''` (clearing a slot); otherwise it reverts to the previous `value` unless `allowFreeText` (default `false`) is set, in which case the raw text commits (custom items). A `selectingRef` flag set in the option `onMouseDown`/`onTouchEnd` handlers makes the blur handler skip its revert when an option tap is landing. `GuardPanel` equipment/satchel use the default (constrained vocabulary → revert unknown text).

### Static data

- **`src/data/constants.js`** — guard names, city names, `GUARD_COLOR_MAP` (single source of truth for guard identity colors), `FALLBACK_COLOR`, section factories, and `createInitialState()`
- **`src/data/materials.js`** — crafting material categories, `ALL_MATERIALS`, `ALL_ITEMS_WITH_CATEGORY` (pre-computed `{ item, category }` pairs for the stash UI), `RESOURCE_NODE_ITEMS`, `ENEMIES`, `WEAPONS`, `ARMOR`, `ACCESSORIES`, `ITEMS`, `WEAPON_STATS`, `ARMOR_STATS`, and `MATERIAL_SOURCES`
- **`src/data/recipes.js`** — all 101 crafting recipes as a static `RECIPES` array; helper functions `minCraftCost`, `craftCities`, `craftCostForCity`, `availableInCity`, `craftStatus`, `shortageCount`, and `derivePrereqUpgrades`. See the shape comment at the top of that file.
- **`src/data/prereqUpgrades.js`** — the `PREREQ_UPGRADES_TO` map (prereq item name → `{ name, stars, isFtIstra }` of the lowest-star recipe it unlocks), used by StashTab for its inline upgrade hints.
- **`src/data/encounterNames.js`** — `ENCOUNTER_NAMES`, encounter id → display name, used by `gameReducers`' `encounterLabel` for log entries.

**`prereqUpgrades.js` and `encounterNames.js` are committed literals on purpose — do not fold them back into a derivation over `RECIPES` / the encounter arrays.** Three tabs are lazily chunked (`CraftTab`, `CampaignTab`, `MoreTab`, plus `SettingsPanel` / `GlobalSearch`) and three are eager, so anything the eager graph touches ships in the entry chunk. Both of these were one small import away from dragging a whole data module onto the critical path: `StashTab` (eager) needed an eleven-entry upgrade map and pulled all 101 recipes; `gameReducers` (eager, via `useGameState`) needed a name for one log string and pulled every encounter's freeform enemy setup, reward and unlock text. Extracting them moved `recipes.js` (38.78 kB raw / 4.80 kB gzip) into the CraftTab chunk and `encounters.js` (31.59 kB / 4.88 kB) into the MoreTab/GlobalSearch chunk — the entry chunk went 371.79 kB → 303.43 kB raw, 99.96 kB → 90.77 kB gzip.

The rule these follow: **the derivation rule is never duplicated, only its output, and a test pins the two equal.** `derivePrereqUpgrades` in `recipes.js` remains the single definition of "lowest-star recipe per prereq" and `recipes.test.js` asserts the literal deep-equals it over the live `RECIPES`; `encounters.test.js` asserts `ENCOUNTER_NAMES` has exactly one entry per encounter id with the matching name, no extras. Adding, renaming or retiering an encounter or a prereq recipe fails those tests with a diff — update the literal, don't reach for the derivation at runtime. Verify with `npm run build`: neither `recipes` nor `encounters` should appear as a `modulepreload` in `dist/index.html`.

Note what is **not** worth doing here, because it was measured (AVE efficiency review): deferring `@sentry/react` behind a dynamic `import()` looks like the same kind of win and is the opposite. The static `import * as Sentry` in `main.jsx` / `ErrorBoundary.jsx` tree-shakes to **11.21 kB / 3.69 kB gzip**; a dynamic import yields the full module namespace and defeats that shaking, rebuilding the chunk at **478 kB** (156 kB gzip) — or **91.63 kB / 30.98 kB gzip** if the `.then` destructures only `init` and `captureException`. Both are far worse than the 3.69 kB of preload they remove. Leave the static imports alone. The same caution applies to `@supabase/supabase-js` (200.71 kB / 51.63 kB gzip, statically imported by `useSupabaseSync` and preloaded on every cold load): deferring it is a genuine ~52 kB gzip win because it is not tree-shaken down to anything, but it turns `client` into async state that every effect keyed on it must tolerate — measure the resulting chunk before assuming the win survives.
- **`src/data/demoSave.json`** — offered by the first-run onboarding overlay; uses the v1 flat shape and goes through `healState(migrateV1(demoSave))` in `loadDemoData`. **Every whole-state replacement path heals** — import (AVE-365), reset (healthy by construction), and demo (AVE-927). `migrateV1` alone only `??`-defaults top-level keys, so the hand-maintained fixture's drift would otherwise reach React state, localStorage, *and* the shared campaign row via `replaceRow` — where the deep merge keeps it forever, seeding AVE-922 from a clean install. Keep the fixture free of retired keys too, so it never reads as a schema reference for shapes the healers discard.

### Guards

8 playable guards: Grigory, Alek, Catherine, Yury, Kharzin, Vera, Pavel, Yana.

Two guards are active at a time (`state.activeParty`, a 2-element name array). The active party is selected in SettingsPanel. The guard tab shows a switcher between the two active guards; `state.activeGuardIdx` tracks which one is currently visible (index into the full 8-guard array, not into activeParty).

**`activeGuardIdx` is local-only and never synced.** It represents which guard tab the local player is viewing — a per-device UI preference. `setActiveGuard` passes `null` as the section name (not `'guards'`). `handleRemoteChange` explicitly preserves the local value, and `SECTION_KEYS` in `useSupabaseSync` does not include it. Do not add it back to the sync section.

Each guard in state has: `name`, `hp`, `maxHp`, `baseAtk`, `baseDef`, `expandedSatchel`, `satchel` (8-slot array of `{ item, qty }`), `equipment` (`{ weapon, armor, accessory, item }`).

**`equipment.item` is the *active item* slot, and anything in `ITEMS` may occupy it — consumables included.** Its purpose is to record what a guard can reach mid-battle, so `Health Potion` belongs there (AVE-548). Options come from `ITEMS`, so an item missing from that array cannot be selected at all: it renders if already set, but clearing the slot loses it for good. That is the class of bug to watch for when adding a reward item — `Raven's Beak Flask` was referenced by a bounty reward while existing nowhere in `ITEMS`.

**Attack and Defense come from `WEAPON_STATS`/`ARMOR_STATS`, never from a recipe's `statBonus`.** The two were transcribed separately and drifted on 26 items, so a craft card promised one number and equipping delivered another (AVE-544); the stats maps proved correct on every one. `recipes.test.js` now asserts the two agree for every item in both tables, with no exceptions list — if an item ever genuinely differs, add it there with a citation rather than loosening the assertion.

**Six starter weapons are non-craftable and sit at 0 attack** — `Iron Short Sword`, `Captain's Blade`, `Iron Hand Axes`, `Guard's Spear`, `Long Bow`, `Iron Hammer`. You begin the game with one, and each is the `prereq` of its ★★ blacksmith upgrade, so they must stay in `WEAPONS` or the prereq becomes permanently unsatisfiable (AVE-545). A test asserts every recipe `prereq` resolves to a known item or recipe name.

**Guard identity colors** are defined in `GUARD_COLOR_MAP` in `src/data/constants.js`. Each entry: `{ key, border, bg, text }` where `key` is the CSS variable suffix (e.g. `'amber'` → `--c-guard-amber-*`). Import from constants — do not redefine this map in component files.

Portrait images live in `public/guards/` named in lowercase (e.g. `grigory.webp`). `GuardAvatar` in `GuardPanel.jsx` falls back to initials automatically on `onError`. **It records *which* `src` failed, not a bare `failed` boolean** — `GuardPanel` is rendered in a fixed position with no key, so switching between the two active guards reuses the same component instance, and a boolean stuck at `true` made every guard viewed afterwards fall back to initials too. One slow or blocked request (offline before the service worker had precached `public/guards/`) took out the portraits for the whole session. Same class as the guard-level `ErrorBoundary` below: **anything stateful under the guard switcher has to be scoped to the guard, because nothing there remounts.**

### Cities

6 cities: Mir, Razdor, Ryba, Silny, Strofa, Vouno.

City state shape: `{ id, name, puzzleQuestDone, bounty1Done, bounty2Done }`. All three are legacy fields kept for save-shape compatibility but no longer drive anything — quest completion moved to `campaign.completedPuzzleQuests` / `campaign.completedBounties` (see Puzzle Quests / Bounties below).

**Prestige (reputation) is never stored.** Always derive it with `cityPrestige(city, campaignId, completedBounties, completedPuzzleQuests)` from `gameReducers.js`. It counts the city's completed **campaign puzzle quest** plus its two completed **campaign bounties** for the active campaign (max 3: 1 puzzle + 2 bounties). Because both are campaign-scoped, reputation shown for each campaign is independent. Do not add a `prestige` field to city state. `CraftTab` also calls `cityPrestige` (for the prestige-≥2 crafting discount) and must be passed `campaignId` + `completedBounties` + `completedPuzzleQuests`.

### Puzzle Quests

24 Puzzle Quests (6 Cities × 4 campaigns, one each), transcribed from the physical companion book, live as **static reference data** in `src/data/puzzleQuests.js` (`PUZZLE_QUESTS`; `puzzleQuestForCity(cityName, campaignId)`). Each entry: `{ id, city, campaign, location }` — `id` is `${slug(city)}-c${campaign}-puzzle`. Unlike bounties, a puzzle quest only needs a location (no targets/conditions/rewards), so it renders inline on the city card rather than as its own detail card/dialog.

Puzzle quests render on the **Cities tab** (`CitiesTab.jsx`) as the existing checkbox row (`.quest-row`), with the campaign's location shown as a subtitle beneath the "Puzzle quest" label. Like bounties, puzzle quests are campaign-scoped and **not** cumulative — the row shows only the active campaign's location.

Per-quest completion is `campaign.completedPuzzleQuests`, an id-keyed tombstone array `{ id, deleted? }[]` — identical shape and mechanics to `completedBounties`/`completedEncounters` (AVE-287): it syncs via the `campaign` section, tombstones un-completes rather than dropping them, and is normalized on load via `normalizeCompletedEncounters`. Reducers: `reduceTogglePuzzleQuestComplete` / `isPuzzleQuestCompleted` in `gameReducers.js`.

Pre-existing saves carried puzzle-quest completion as the single non-campaign-scoped `city.puzzleQuestDone` flag. On load, `migrateLegacyPuzzleQuestDone` (`useGameState.js`, used by both `migrateV1` and `healState`) converts a `true` flag into a `completedPuzzleQuests` entry for that city under whatever campaign was active in the save. The migration is strictly **one-shot per city** (AVE-370): the flag is **cleared** after converting (unlike `bounty1Done`/`bounty2Done`, which are inert), and a city is skipped when any `completedPuzzleQuests` entry for it already exists — live or tombstoned, any campaign. It used to re-run on every load, which resurrected un-completed quests on reload (appending duplicate ids — `normalizeCompletedEncounters` now dedupes, keeping the first occurrence) and leaked completion into whatever campaign was active.

### Bounties

48 Bounty Quests (6 Inns × 4 campaigns × 2), transcribed from the physical companion book, live as **static reference data** in `src/data/bounties.js` (`BOUNTIES`; `bountiesForCity(cityName, campaignId)`). Each bounty: `{ id, inn, city, campaign, name, location, targets, conditions, rewards }` — `city` is derived from the Inn prefix (e.g. `Mir: The Clayhorn` → `Mir`) and `id` is `${slug(city)}-c${campaign}-${slug(name)}`. `targets`/`conditions`/`rewards` are verbatim freeform strings (same convention as the encounter `enemies`/`reward` fields).

Bounties render on the **Cities tab** (`CitiesTab.jsx`), styled with the Training Yard / Spirit Boss `.encounter-*` primitives (card + bottom-sheet detail dialog). Each city card shows only the **two bounties for the active campaign** — bounties are Inn- and campaign-scoped, **not** cumulative.

Per-bounty completion is `campaign.completedBounties`, an id-keyed tombstone array `{ id, deleted? }[]` — identical shape and mechanics to `completedEncounters` (AVE-287): it syncs via the `campaign` section, tombstones un-completes rather than dropping them, and is normalized on load via `normalizeCompletedEncounters`. Reducers: `reduceToggleBountyComplete` / `isBountyCompleted` in `gameReducers.js`.

### Stash

`state.stash` is a plain object mapping item name → integer count. A count that reaches 0 is **kept as a `0` entry (map tombstone), never deleted** (AVE-369): the server merge preserves keys absent from the payload, so a deleted key never propagated and the write's own Realtime echo resurrected the item on the deleting client (same class as AVE-362). Read sites treat 0 and absent identically (`?? 0` / `> 0` filters), and `compactTombstones` drops 0-count keys in solo mode / on leaveCampaign (AVE-368). All 60+ material names are defined in `MATERIAL_CATEGORIES` in `materials.js`.

**The same rule applies to every growable object map, not just `stash` (AVE-925).** `withUndoTombstones` negates keys present in current state but absent from the undo snapshot via the shared `withUndoMapTombstones(prev, curr, neutral)` helper: `stash` uses `0`, `campaign.ftIstraBuildings` uses `'not_owned'`. The `neutral` value must be one every read site already falls back to for an absent key — `BUILDING_STATES`/`ftIstraBuildings[name] ?? 'not_owned'` in `CampaignTab` — otherwise it is a real value, not a tombstone. `ftIstraBuildings` was missed originally because the function's doc block classed everything outside the id-keyed arrays as "scalar fields and guard objects [that] are explicit-value writes"; a map that grows is neither, and undoing the *first* state change to a building (which adds the key) was resurrected by the merge and its own echo. Note the asymmetry with `stash`: `compactTombstones` deliberately does **not** GC `'not_owned'` entries, because unlike a 0-count stash key it is a value the user can set on purpose, and the map is bounded by `FT_ISTRA_BUILDINGS.length`. `BUILDING_STATES` / `BUILDING_STATE_LABELS` live in `src/data/buildings.js`, not `CampaignTab`, so tests can assert against the real constant without making the component file a mixed component/constant module.

Any string that doesn't match a predefined material name can be added as a **custom item**. Custom items are stored in `state.stash` like any other item and rendered under a "Custom items" category. `ALL_KNOWN_ITEMS` (a `Set` exported from `materials.js`) is the predefined-item membership test.

Stash items that appear as a `prereq` in any recipe show an inline **"→ Item Name ★★★"** upgrade hint in the stash UI, sourced from `PREREQ_UPGRADES_TO` in `prereqUpgrades.js`. The lowest-star recipe matching each prereq is shown.

### Stonebound

`state.stonebound`: `{ max: number, locations: Array<{ id, selection, count }> }` (plus a `deleted` tombstone once a location is removed — see AVE-287). `selection` is chosen from a grouped `<select>` in `StashTab` (Cities / Resource nodes / Enemy drops) and `count` is the cubes on that location.

There is deliberately **no `type` field** (retired in AVE-874). It used to be seeded as `''` by `reduceAddStoneboundLocation`, healed on every load, and shipped through the field-level merge on every stash write — but nothing ever derived it from the selection and nothing ever read it, so it was `''` for every location forever. The docs claimed it was "derived from the selection", which was never true and would have misled anyone building grouping or per-type icons on top of it. Same orphaned-state class as AVE-795. `healState` drops the key rather than healing it, so a save or campaign row that still carries one stops resurrecting it.

**A retired key that is actually present is negated (`type: null`), not silently dropped (AVE-922).** Dropping it was assumed harmless — the deep merge preserves keys absent from a payload, so an old row simply kept an inert `''`. It is not harmless: `extractSection(local)` no longer carries the key, so no future payload can ever remove it, and the row and local state diverge permanently. Both echo guards in `applyRemoteRow` compare the **raw** incoming value against values that lack the key (current local, and the `selfWrites` buffer — which holds exactly what `extractSection` produced), so every Realtime echo of our *own* write is misread as a genuine remote change: `onRemoteChange` fires, the undo snapshot is wiped ~1s after every stash edit, and two edits inside one debounce-plus-echo window let the older value clobber the newer one (the AVE-314 symptom). Emitting `type: null` makes the next write clear the stored key — `jsonb_typeof` is `'null'`, which matches neither the object nor the array branch of `deep_merge_jsonb`, so it falls through to `jsonb_set` and overwrites — after which the echo deep-equals local again and suppression is restored for that row with no data migration. The negation is conditional (`type === undefined ? {} : { type: null }`): a location that never had the key must not gain a `null`, or the healer would break the same invariant from the other direction. `campaign.locations.bounties` (AVE-795) is negated identically in `healCampaignSection`. If a consumer for `type` ever appears, derive it then.

### Craft tab

`CraftTab` is a **read-only** component. It receives `stash`, `sil`, `lux`, `activeParty`, `guards`, `cities`, and `onShowSource` as props and derives all display state from them. It owns no state beyond local UI state (search string, active filters). Do not add crafting state to `useGameState` — the tab intentionally introduces no new persistence.

**Combined inventory for craftability:** `buildCombined(stash, activeGuards)` merges the Fort Istra stash with the active guards' satchel contents. All craftability checks (`craftStatus`) and have/need counts run against this combined total — items a guard is carrying count toward the "have" amount.

**`RecipeCard` is `memo`'d and the search term is deferred — both halves are load-bearing, and neither is testable.** The unfiltered list is up to 90 cards / ~2,300 DOM nodes, so every keystroke used to re-render all of them. Measured in Chromium against a production build at 6× CPU throttle, using the Event Timing API (the input-to-paint measurement Chrome's INP is built on), median of 3 runs:

| variant | worst keystroke | median keystroke |
|---|---|---|
| neither | 280 ms | 112 ms |
| `memo` only | 256 ms (−9%) | 88 ms (−21%) |
| `useDeferredValue` only | 144 ms (−49%) | 56 ms (−50%) |
| **both** | **80 ms (−71%)** | **40 ms (−64%)** |

Note what those rows say: **`memo` alone is worth ~9%, inside the noise band — do not conclude from that it is the removable half.** On top of the deferred term it takes 144 ms → 80 ms, because deferral is what makes the render interruptible and reduced per-slice work is what lets each slice finish. They are complements. The worst case is not typing but *clearing* a search (25 → 84 cards re-expanding), which is why the fix targets card mounts rather than the arithmetic — `craftStatus` over all 101 recipes is 40 µs, `availableInCity` 16 µs, `parseItemReq` 5 µs, so memoizing any of those buys nothing.

Two ways this silently reverts, both with green tests: switching the `filtered` memo back from `deferredSearch` to `search`, or passing `RecipeCard` an inline lambda / object literal from its single call site (all eight of its props are currently primitives, `useMemo`'d values, or a setState function). `src/components/CraftTab.test.jsx` covers the tab's **behaviour** and is deliberately invariant to this change — it passes identically with and without it, which was verified, along with its failing on a seeded behaviour break. The perf property genuinely cannot be asserted in jsdom: there is no layout and no concurrent scheduling to observe, so a render-count proxy would be brittle theatre. The comments at the two sites plus this table are the guard.

Neither change touches the tab's own mount (72 ms warm tab switch for 90 cards, unchanged), and the cold path into Crafting is dominated by its lazy chunk. Capping the rendered list would fix both — it was considered and rejected: Crafting is a reference surface, and scrolling the whole catalogue is the feature. At 4× throttle the unfixed worst case was 184 ms, already inside Chrome's "good" INP band, so this is specifically a low-end-device win.

**Filters:**
- **Search** — matches recipe names, ingredient names, city names, and prereq item names
- **Type** — All / Weapon / Armor / Accessory / Item (dropdown)
- **City** — filters to recipes craftable in a specific city; affects cost display (city-specific Sil prices) and whether the prestige discount applies. Cities with prestige ≥ 2 show a `✦` suffix in the dropdown.
- **Star tier** — minimum star pill filter (All / ★ / ★★ / ★★★ / ★★★★ / ★★★★★); 5-star tier is styled in red to distinguish Ft. Istra items
- **Can craft** — hides recipes not currently `'ready'`

Results are grouped by type (Weapon, Armor, Accessory, Item).

**Prestige discount:** When a city with prestige ≥ 2 is selected, material quantities use `qty2R` (the reduced amount) instead of `qty` for standard (non-Ft. Istra) recipes. Discounted ingredients show the original quantity struck through with the reduced quantity beside it. A `2★` badge appears on the card footer when the discount is active.

`craftStatus(recipe, stash, sil, lux, selectedCity, cityPrestigeLevel)` returns `'ready' | 'partial' | 'missing'`:
- **ready** — all materials satisfied AND currency satisfied (city-specific or minimum Sil price, or Lux for Ft. Istra items)
- **partial** — at least one material present but not all requirements met
- **missing** — none of the required materials are in stash

Guard-restricted recipes (`limitedTo` is non-empty) are hidden entirely from the list if no matching guard is in `activeParty`. When a matching guard is active, a restriction note is shown on the card.

Recipe data lives entirely in `src/data/recipes.js`. Each recipe has this shape:

```js
{
  name: string,
  type: 'Armor' | 'Weapon' | 'Accessory' | 'Item',
  city: string,           // human-readable, comma-separated for multi-city
  isFtIstra: boolean,
  stars: 1–5,             // 5 = Ft. Istra endgame tier (shown in red)
  statBonus: string|null, // e.g. '3⛊' or '2👊'
  bonusChip: string|null,
  effect: string|null,    // accessories/items only
  craftCost: number | { CityName: number } | null,
  luxCost: number|null,
  prereq: string|null,    // item that must be equipped first
  itemReq: string|null,   // special ingredient (apothecary items)
  limitedTo: string[],    // guard names; empty = available to all
  materials: Array<{
    name: string,
    qty: number,          // base quantity required
    qty2R: number|null,   // reduced quantity at prestige 2+ in a qualifying city; null = no discount (Ft. Istra, speaking-stone items)
    isSpeakingStone: boolean,
  }>,
}
```

Guard-restricted recipes (`limitedTo` is non-empty) are hidden entirely from the list if no matching guard is in `activeParty`. When a matching guard is active, a restriction note is shown on the card.

### MATERIAL_SOURCES

`MATERIAL_SOURCES` is a plain object exported from `materials.js` mapping item name → source descriptor. It is the sole data source for `MaterialSourcePopup`. Each entry has up to seven optional fields:

```js
{
  enemies?: string[],                         // enemy names that drop this material
  nodes?: string[],                           // resource node names
  ftIstra?: { label: string, luxPer4: number }, // Ft. Istra acquisition (shown under nodes if nodes exist, standalone otherwise)
  market?: { city: string, price: number }[], // cities that sell it and the Sil price
  sell?: { city: string, price: number }[],   // cities that buy it and the Sil sell price
  ftIstraSell?: number,                       // Ft. Istra Apothecary sell price in Lux Essence (not Sil)
  questReward?: true,                         // no fixed source — quests/events/story progression
}
```

**An entry's absence is not neutral — `MaterialName` only makes a name tappable when `MATERIAL_SOURCES[item]` exists**, so a material with no entry renders as dead text and reads as a broken control rather than as "unknown". That is why the 15 speaking stones, the 9 `special` ingredients and `Cooked Fish` carry `questReward: true` (AVE-548): they genuinely have no market, node or enemy source — the game deliberately does not tell you where they come from — and saying so is an answer. `materials.test.js` asserts every non-gear material has an entry, so a newly added material cannot silently become untappable.

**Membership of `speaking_stones` deliberately differs from the companion spreadsheet's stone list, in both directions.** `Jade`, `Black Diamond` and `Ancient Roots` live in `special`, and `Diamond` in `ores`, because each is a single physical item usable either as an ingredient or as a stone — tracking one quantity in one category is the point, and an item in two categories renders two stash rows and two search hits (AVE-546). `Topaz`, `Peridot`, `Coral` and `Pearl` are stones (confirmed against the physical game) that the spreadsheet's bonus table omits. Do not "reconcile" these against the spreadsheet.

### File downloads

**Every save-file download goes through `downloadJson(filename, text)` in `src/utils/downloadUtils.js` (AVE-941)** — Settings → Export (`exportState`), the corruption banner's Download backup, and the `ErrorBoundary` crash screen's Export save. It attaches the anchor to the document before clicking and revokes the object URL on a **later task**, not in the same tick as `.click()`: revoking invalidates the URL immediately, and whether the click-initiated fetch has already read the blob is not guaranteed across engines. It returns a boolean rather than throwing — one of its callers *is* the `ErrorBoundary`, so a throw would be recursive. Callers surface only the failure; the browser's own download UI is the success confirmation. All three of these controls sit directly beside a destructive one (Dismiss, Reload, Reset), which is what makes a silent no-op expensive: the corruption banner's Dismiss clears `guards_ledger_corrupted_backup`, so a download that quietly produced nothing loses the raw save for good. Every call site must act on that boolean — `SettingsPanel`'s Export JSON and the copy of it inside the Join confirm (`exportError`), `App.jsx`'s save-error banner (`exportProblem`), the corruption banner, and the `ErrorBoundary`. The save-error banner is the sharpest case: it exists *because* browser storage is full or blocked, which is exactly when the download is most likely to fail, and its copy tells the player to export now so they don't lose progress. Do not reintroduce a per-call-site `URL.createObjectURL` — `grep -c 'URL.createObjectURL' src/` should stay at 1.

### Testing

`src/hooks/gameReducers.test.js` covers all pure reducer functions. `src/hooks/useSupabaseSync.helpers.test.js` covers the pure section ↔ column helpers (`extractSection`, `applyRemoteSection`, `normalizeRow`, `normalizeCampaignCode`, the `guard_N` column helpers). Component tests live beside their components (`Autocomplete.test.jsx`, `CampaignTab.test.jsx`, `CitiesTab.test.jsx`, `CorruptionBanner.test.jsx`, `GuardPanel.test.jsx`, `SettingsPanel.test.jsx`, `UpdateBanner.test.jsx`); they carry a `// @vitest-environment jsdom` pragma on line 1 and use `React.createElement` rather than JSX, since the automatic-JSX-runtime lint config flags a bare `React` import as unused. Run everything with `npm test`.

**Vitest and `vite build` do not share a Vite.** Vitest 3 runs on its own bundled **Vite 7**, which transforms with **esbuild**; `npm run build` runs the **Vite 8** in `package.json`, which transforms with **oxc**. That is why `vite.config.js` is a function of `({ mode })` and sets `esbuild: { jsx: 'automatic' }` **only** when `mode === 'test'`: Vitest needs it to import JSX-authored components without a bare `import React` (dropping it fails 41 tests with `React is not defined`), while the build must not see it — `@vitejs/plugin-react` already sets the oxc equivalent there, and Vite 8 warns and *discards* the esbuild option whenever both are present. Setting the oxc option at the top level instead does not help: it never reaches Vitest's Vite 7. If a future Vitest adopts Vite 8, collapse the gate rather than setting both.

**`fireEvent.focus` does not move `document.activeElement`.** Any component that calls `.blur()` (or `.focus()`) on itself is untestable with it — the call silently no-ops and the test passes while the real browser path is broken. That is exactly how AVE-924's Enter-double-commit and Escape-commits-anyway survived two tests written to pin them. Use a real `input.focus()` whenever the behaviour under test involves focus moving. Only two places in `src/` touch focus imperatively — `DraftInput`'s `e.currentTarget.blur()` and `useDialogA11y` — and `useDialogA11y` is the only code that reads `document.activeElement`; both are covered with real focus. `Autocomplete` merely *reacts* to focus/blur events and never queries `activeElement`, so `fireEvent.focus`/`fireEvent.blur` are faithful there and its tests are fine as written.

**`useDialogA11y`'s `FOCUSABLE` applies its exclusions per clause.** A natively-focusable element matches `input:not([disabled])` regardless of its tabindex, so a trailing `[tabindex]:not([tabindex="-1"])` clause does **not** filter one out — that clause is an *additional* selector for non-natively-focusable elements (a div with `tabindex="0"`), not a constraint on the others. `SettingsPanel`'s deliberately-unreachable file input (`display:none` + `tabIndex={-1}` + `aria-hidden`, AVE-785) was therefore counted as a stop in the trap. It was harmless only because it sits mid-list: the trap special-cases `items[0]` and `items[last]` alone, and a hidden element in either position makes `first.focus()` a silent no-op that leaves focus on `<body>` — outside the dialog, where `document.activeElement` never matches either boundary and Tab escapes the modal entirely. Every clause now carries `:not([disabled]):not([tabindex="-1"]):not([aria-hidden="true"])`. The exclusions are **attribute-based on purpose**: jsdom has no layout, so a real visibility test (`offsetParent`, `getClientRects`) would filter out every element under test and break the trap in the very tests that pin it.

### Supabase setup

For local development with multiplayer enabled:

1. Run `supabase/schema.sql` in the Supabase SQL editor (fresh installs). For a database created before AVE-83, instead run the one-time `supabase/migrations/0001_split_guards_per_column.sql` to split the old single `guards` column into per-guard columns.
2. Run `supabase/migrations/0002_field_level_merge.sql` to install the `merge_section` RPC and `deep_merge_jsonb` helper. (Idempotent `CREATE OR REPLACE` — safe to re-run.)
3. Run `supabase/migrations/0003_array_merge.sql` to install the `merge_jsonb_array_by_id` helper and the array-aware update to `deep_merge_jsonb`. (Idempotent `CREATE OR REPLACE` — safe to re-run.)
4. Run `supabase/migrations/0004_tombstone_deletes.sql` to convert existing `campaign.completedEncounters` string arrays to the id-keyed `{ id }` shape used by tombstone deletes (AVE-287). Data-only, no function change; idempotent (only touches rows still holding strings).
5. Run `supabase/migrations/0005_plain_array_lww.sql` to make non-id-keyed arrays (guard satchels, `activeParty`) replace wholesale instead of merging as a set union — the union resurrected deleted satchel items (AVE-362). Requires 0004 first. (Idempotent `CREATE OR REPLACE` — safe to re-run.)
6. Run `supabase/migrations/0006_atomic_merge_section.sql` to make `merge_section`'s read-merge-write atomic (a single `INSERT ... ON CONFLICT DO UPDATE` instead of a separate `SELECT` then computed write), closing a lost-update race between two concurrent writes to the same section (AVE-373). (Idempotent `CREATE OR REPLACE` — safe to re-run.)
7. **Run `supabase/migrations/0007_row_generation.sql`** to add the `generation` column and replace `merge_section` with the generation-aware **four-argument** version, so a full-row reset/import gates out a co-player's stale in-flight merge (AVE-527). **Required, not optional hardening** — `upsertSection` and `flushQueue` always send `expected_generation`, and PostgREST resolves an RPC by argument *names*, so a database still on the three-argument function rejects **every** write with `PGRST202` (and `replaceRow`'s `select('generation')` fails with `42703`). Reads and Realtime keep working, so the app looks connected — campaign pill and all — while writing nothing and parking the sync dot on red. (Idempotent: `add column if not exists` + `CREATE OR REPLACE`.)
8. **Run `supabase/migrations/0008_campaign_membership.sql`** to scope campaign access to membership instead of granting the whole table to anyone holding the anon key (AVE-971). Adds `campaign_members`, `is_member`, `join_campaign`, an atomic `create_campaign`, and replaces the three `using (true)` policies with membership ones scoped `to authenticated`. **Rollout order is load-bearing: (a) enable Anonymous sign-ins in Authentication → Providers, (b) deploy the client, (c) apply this migration.** Applying the migration first cuts off every already-running client at once, mid-session. The client is safe to run against an unmigrated database because `ensureMembership` and `createCampaign` treat PostgREST's `PGRST202` ("could not find the function") as "this database has no membership model" and fall through to the pre-0008 behaviour — without that tolerance the deploy window stops sync for everyone, and forgetting the migration entirely would half-break the app rather than leaving it as it was (the AVE-870 failure mode). Anonymous sign-ins must be on *before* the client ships, since a failed sign-in degrades to local-only. (Idempotent.)
9. In the Supabase dashboard go to **Database → Replication** and enable Realtime for the `campaigns` table (the schema also attempts this via `alter publication`)
10. In **Authentication → Providers**, enable **Anonymous sign-ins**. Required by step 8: `postgres_changes` authorizes Realtime delivery against the socket's JWT, so without a session the membership policies silently sever inbound updates while outbound writes keep failing.
11. Copy `.env.example` to `.env` and add `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`
12. `npm install @supabase/supabase-js`

Without these env vars the app runs as a local-only tool — no errors, sync is simply disabled.

**Every file in `supabase/migrations/` must appear exactly once in the list above.** This list is the only place in the repo that enumerates them (neither `README.md` nor `docs/sync.md` does), so a migration missing from it is a migration nobody runs — which is exactly how `0007` came to be skipped on a live database (AVE-870). `schema.sql` is only correct for **fresh** installs; it already contains the `generation` column and the four-argument function, so an existing database upgraded step-by-step is the case that breaks. When adding a migration, add its step here in the same commit.

**Access control (AVE-971).** Before `0008` the three policies were `using (true)`. An RLS `using` clause is evaluated per row and cannot see the query's `WHERE`, so a single unfiltered `GET /rest/v1/campaigns?select=id` returned every campaign id and one `PATCH` could overwrite any campaign — AVE-104's wider keyspace raised the cost of *guessing* an id and left the cost of *listing* every id at one request. The campaign code is now an enforced capability: `join_campaign(code)` takes the code as an argument, so it grants access without ever permitting a listing, and it deliberately does **not** verify the campaign exists (checking would make it an oracle for "is this code real"). Two cheaper designs fail on the same constraint and fail *silently*: a request-header policy is invisible to Realtime (no `request.headers` on the websocket), and revoking `select` in favour of a `security definer` read breaks `postgres_changes`, which authorizes delivery via RLS `select` on the subscribing user. That is why anonymous auth is used — not as a login, but to put a subject in the JWT. Note the role: a Supabase anonymous user gets the **`authenticated`** role with an `is_anonymous: true` claim, *not* `anon`, so policies scoped `to authenticated` cover all real traffic while `anon` loses table access entirely. `create_campaign` is one transaction on purpose — join-then-insert would leave a stray membership row on a `23505` id collision, which is a permission grant on a stranger's campaign.

**The client establishes access before every network call.** `ensureSession` memoizes one anonymous sign-in (cleared on failure, so a paused free-tier project or captive portal stays retryable), `ensureMembership` joins once per campaign id, and `ensureAccess` combines them and returns a boolean rather than throwing — a failed sign-in degrades to local-only play and queues the write, it never blocks a local edit. Two orderings are load-bearing: `join_campaign` must precede `joinCampaign`'s `SELECT` (a non-member sees zero rows, so selecting first reports "No campaign found" for a correct code), and the session must precede `subscribe` (a channel opened before the JWT exists is never delivered to). The boot path re-joins a stored campaign id, which is what makes the migration invisible to existing players — a backfill is impossible because the migration has no `user_id` to write. `useSupabaseSync.membership.test.jsx` pins the ordering specifically, because a happy-path test passes against a mock even when the order is wrong.

To verify a database is fully migrated, run:

```sql
select p.proname, pg_get_function_identity_arguments(p.oid) as args
from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public'
  and p.proname in ('merge_section', 'deep_merge_jsonb', 'merge_jsonb_array_by_id')
order by p.proname, args;
```

Expect exactly one `merge_section`, with `campaign_id text, section_name text, payload jsonb, expected_generation bigint`, plus `deep_merge_jsonb(jsonb, jsonb)` and `merge_jsonb_array_by_id(jsonb, jsonb)`. After `0008` also expect `is_member(text)`, `join_campaign(text)` and `create_campaign(text, jsonb)` — add those three names to the query's `in (...)` list to check them. A three-argument `merge_section` means `0007` has not been applied. Note that `0005` is a `CREATE OR REPLACE` of `deep_merge_jsonb` with an unchanged signature, so this query cannot distinguish "0005 applied" from "0003 only" — if deleted satchel items reappear (the AVE-362 symptom), re-run `0005`.

**Functions and policies existing does not mean access is enforced — check `relrowsecurity` separately.** A policy on a table with RLS *disabled* is stored, listed by `pg_policies`, and filters nothing; every query keeps working and the table stays fully readable, so there is no symptom to notice. `0008` therefore enables RLS itself rather than relying on `schema.sql`, which carries the line but is fresh-installs-only — the production database predates the file (`schema.sql` was first committed in `c91dc8f`, together with the table definition), so replacing `using (true)` with membership policies there swapped one set of inert policies for another. Verify enforcement, not presence:

```sql
select relrowsecurity as rls_on, relforcerowsecurity as rls_forced
from pg_class where oid = 'public.campaigns'::regclass;
```

`rls_on` must be `true`. The end-to-end check is the harness in `scratchpad/RLS-PROCEDURE.md`, which impersonates a non-member (`set local role authenticated` plus forged `request.jwt.claims`) and asserts it sees **zero** rows — and self-tests that the impersonation took before trusting its own result, so a "sees nothing" cannot come from a broken harness. Do not treat a table as protected on the strength of the policy list alone.

### PWA

`vite-plugin-pwa` (`vite.config.js`) generates the service worker and the web app manifest. Four rules, the middle two learned from AVE-939:

- **`registerType` is `'prompt'`, never `'autoUpdate'` — the lazy tabs depend on it.** `autoUpdate` emits `skipWaiting()` + `clientsClaim()` + `cleanupOutdatedCaches()`, so a new deploy took over the page that was *already running* and deleted the precache underneath it. That page still holds the **old** entry chunk, whose `lazy()` calls name old hashed filenames (AVE-292) — now absent from the precache and 404 on the origin, since Cloudflare Pages serves only the current deployment. The next tap on Crafting / Campaign / More / Settings / Search died with `Failed to fetch dynamically imported module`, while Guards / Cities / Stash (statically bundled into the entry chunk that had already downloaded) kept working — the exact shape of the reported symptom. Cache-first `index.html` made the window very wide: a backgrounded PWA can boot the stale bundle long after the deploy, so it was not just a few minutes per release. With `'prompt'` the new worker waits, the old one keeps serving this session's chunks for its whole life, and the player takes the update when they choose. Note the irony worth preserving: `autoUpdate` is what *created* the 404 — without `skipWaiting`, the old worker would have served the old chunks from its own precache regardless of what shipped.
  - Registration therefore lives in `src/main.jsx` (the only module that may import `virtual:pwa-register`), and `injectRegister: null` stops the plugin injecting a second, competing registration. `main.jsx` also polls `registration.update()` hourly — a standalone PWA on a table can go hours without a navigation, and a navigation is otherwise the only thing that checks.
  - `src/utils/swUpdate.js` is the bridge from that registration to `UpdateBanner`. It exists because Vitest cannot resolve `virtual:pwa-register` (so no component may import it) and because the worker can report a waiting update *before* React mounts — a plain event would be missed, so the module holds the state and `UpdateBanner` reads it through `useSyncExternalStore`.
  - `src/utils/chunkReload.js` is the backstop for the failure that already escaped: it listens for `vite:preloadError` and reloads **once per distinct failing chunk URL**, recorded in `sessionStorage`. Keyed by URL, not a bare "tried once" flag — one reload fixes a stale hash, so a URL failing twice is a broken build that must surface instead of spinning, and a second deploy later in the same session produces different hashes and so earns its own retry. It deliberately does **not** cancel the event: the rethrow still reaches the tab `ErrorBoundary` (which already detects chunk errors and offers Reload), so a blocked reload degrades to today's behaviour rather than a blank tab. Cancelling would make Vite's helper resolve `undefined` and turn an accurate chunk-error fallback into a confusing `cannot read .default` TypeError.
  - To verify after a build: `dist/sw.js` contains `skipWaiting` **only** inside the `SKIP_WAITING` message listener, contains no `clientsClaim`, and `dist/registerSW.js` does not exist.


- **The `manifest` block in `vite.config.js` is the only manifest.** The plugin injects the link tag into `index.html` at build time. Do not hand-write a manifest link in `index.html` and do not add a `public/manifest.json`: a document may carry only one manifest link and the user agent uses the **first** in tree order, so a hand-written `/manifest.json` (a file that never existed) shadowed the real one with a 404 and the app was treated as having no manifest — no Android install prompt, no standalone display, none of the declared icons or colours. iOS masked it entirely, because it reads the `apple-mobile-web-app-*` meta tags instead; keep those, they are complementary, not redundant.
- **`workbox.globPatterns` must cover every shipped asset extension.** It listed five image formats and omitted `webp` — the one format actually used, by the eight guard portraits in `public/guards/`. They were the only referenced assets left out of the precache, so offline every guard fell back to `GuardAvatar`'s initials. That fallback is the correct backstop and stays; precaching just stops it firing.

- **`apple-touch-icon` must point at a PNG.** iOS ignores an SVG here, and it does not fall back to the default `/apple-touch-icon.png` once an explicit link exists — so the home-screen icon became a screenshot of the page. `index.html` pointed at `pwa-192x192.svg` while `public/apple-touch-icon.png`, a purpose-built 180×180 (the size iOS asks for), shipped and was precached but was never referenced. This is iOS-only by construction: it reads the `apple-*` tags *instead of* the generated manifest, so nothing in the `manifest` block can cover for it.

To verify after a build: `grep -c 'rel="manifest"' dist/index.html` is `1`, the `apple-touch-icon` href ends in `.png` and that file exists in `dist/`, and each portrait filename appears in `dist/sw.js`.

### Deployment

The live app is deployed to **Cloudflare Pages** at `https://isofarian.averageideas.dev` (the canonical production URL).

There is also a GitHub Pages deploy workflow (`.github/workflows/deploy.yml`) that triggers on pushes to the **`first-draft`** branch. **This is intentional and must not be "fixed" or cleaned up.** The `first-draft` branch deliberately holds an early-draft snapshot of the codebase so it can be deployed and compared side-by-side against the current version — it exists to showcase the difference between the first draft and the latest code. The workflow targeting `first-draft` (rather than `main`) is therefore correct by design. Do not assume it is dead config, and do not point it at `main`.
